# Suite Stabilization Plan

PatchHive's specialist engines now run in-process through the unified backend,
their canonical frontends live in `products/<product>/frontend/`, and suite data
uses the shared SQLite path. Stabilization is no longer a migration exercise;
it is enforcement of the architecture that now exists.

HiveCore remains a separate control-plane concern and is outside this plan's
specialist cleanup work.

## 1. Prevent structural drift

- Keep product identity, route claims, capabilities, health contracts, and
  safety boundaries in `services/patchhive-backend/registry/products/*.toml`.
- Require every specialist backend to expose a reusable `init_runtime()` and
  `router()`; standalone `main.rs` files stay thin launchers over that engine.
- Require every specialist frontend at its canonical `frontend/` path to use
  `@patchhivehq/ui-v3` and `@patchhivehq/product-shell`.
- Reject new `frontend-v2`, `frontend-v3`, and `frontend-legacy` specialist
  trees in suite drift checks.
- Keep one root `.env` and one `PATCHHIVE_DB_PATH`; product-local env files and
  databases are compatibility views, not independent state.

## 2. Keep verification warning-free

- Run formatting, locked checks, tests, and
  `cargo clippy --all-targets -- -D warnings` for changed Rust packages.
- Build every changed frontend and all shared-package consumers it affects.
- Keep suite drift, frontend dependency smoke tests, export validation, and
  Docker builds green.
- Treat CodeQL extraction-quality notices as genuine diagnostics. Improve build
  fidelity where possible and document upstream extractor limits rather than
  hiding warnings.

## 3. Preserve evidence and safety contracts

- Persist all first-class findings produced inside a configured input scope;
  paginate complete retained evidence rather than truncating it after analysis.
- Keep run trigger (`operator`, `schedule`, `webhook`, `orchestration`) separate
  from target selection (`direct`, `discovery`).
- Enforce repository opt-outs, deny rules, trusted-test policy, existing-PR
  detection, product PR limits, and the suite ceiling before external writes.
- Only typed passed validation may produce a non-draft autonomous PR.
- Keep product decisions narrow: diff policy is not merge readiness, review
  quiet is not approval, and missing evidence is never proof of safety.

## 4. Maintain shared seams

Extract a backend or frontend seam when the same stable behavior appears in two
products, before a third private copy lands. Good shared seams include auth,
rate limiting, SQLite pooling, startup diagnostics, schedules, repository
policy, GitHub transport, model discovery, shell layout, dashboard controls,
progressive lists, and activity timelines. Product scoring, evidence meaning,
report voice, and safety decisions remain product-owned.

## 5. Exercise the real suite

The sandbox fixtures should cover read-only scans, degraded permissions,
history and detail retrieval, schedule execution, discovery, comment/status
publishing, held patches, rejected patches, validated draft delivery, and PR
lifecycle monitoring. Tests must be bounded, attributable, and safe to clean up.

## Completion criteria

- `npm run check:suite-drift` reports no structural drift.
- All active Rust and frontend verification is warning-free.
- A fresh product generated by `scripts/new-product.sh` starts with the
  canonical specialist UI and a unified-backend-mountable engine.
- Canonical docs contain no active specialist migration instructions.
- Standalone exports are reproducible from the monorepo without hand edits.
